BPMN extension

Data required for optimisation and simulation is provided through BPMN extension elements, i.e.

  • extension elements for nodes (except timer events),
  • extension elements for timer events, and
  • extension elements for sequence flows.

The XML-schema definition for these extensions is provided in BPMNOS.xsd.

Attributes

Information is provided via attributes. Within an <bpmnos:attributes> container any number of <bpmnos:attribute> elements can be provided to define attributes. For each attribute the following fields can be provided

  • id: a unique identifier,
  • type: the type of the attribute, a scalar type or the shape of an object as described below,
  • name: the name of the attribute and optionally, an initial assignment
  • objective: an optional field indicating whether the attribute value contributes to a global objective which must be either maximize or minimize, and
  • weight: an optional decimal indicating a multiplier for the objective function which must be provided if objective is set.

The scalar types are integer, decimal, boolean and string; an array is an object, e.g. string[]. Only an attribute of type boolean, integer or decimal may contribute to the objective.

Objects

An attribute whose type is not a single scalar type is an object, i.e. an array or a structured value. Its type states its shape: a base, which is a scalar type or a list of fields { name: type, ... } each with a type of its own, followed by any number of dimensions, each written [n] if its size is fixed and [] if it is open. The dimensions are read from left to right in the order of the indices, and each field has dimensions of its own, so that an access has the shape of the type:

Type Access
integer[10] location[i] with i <= 10
boolean[3][4] grid[i][j] with i <= 3 and j <= 4
{ cost: decimal, flags: boolean[] }[] facilities[i].cost, facilities[i].flags[j]
{ x: decimal, y: decimal } depot.x
<bpmnos:attribute id="Location" name="location" type="integer[10]" />
<bpmnos:attribute id="Facilities" name="facilities" type="{ cost: decimal, flags: boolean[] }[]" />

Objects may be declared as global, data and status attributes. They are numbered separately from the scalar attributes, so that the index of a scalar attribute never depends on the objects declared: the global objects come first, and the objects a scope declares follow those of its enclosing scopes. An object cannot be the attribute of a choice, cannot carry the objective, and is neither the instance nor the timestamp.

An object may be initialised by a literal, name="depot := { x := 0.0, y := 0.0 }", which every instance shares, or by an assignment computed when its scope is created, such as name="destinations := destinations(location)" with a lookup returning an array; the instance data may then give it no value, and a global object may only be initialised by a literal. Otherwise an object takes the value the instance data gives it or undefined values, its sizes coming from its type, from the size declarations of the instance data, and from its value, as described for the static data provider. An object is created with the status or data it belongs to: a global object with the global state machine, a data object with the state machine of its scope, and a status object with the status of the token entering its scope, from which it is removed when the scope is left.

An expression reads an object through an access path, in which every index, counting from one, takes the next dimension and a field follows once every dimension is indexed: facilities[i].cost, grid[i][j] and depot.x read values, whereas facilities.cost is refused, since facilities is an array. A path used as a value must address a scalar value. An array of scalar values with a single dimension, named by an attribute or addressed by a path such as location, facilities[i].flags or grid[i], may be aggregated, sum(grid[2]), tested for membership, 3 in location, and iterated in an aggregation, min{ d | d in departures, d >= timestamp }; an object is never used as a value. The aggregation aggr{ expression | i in m..n, j in X, conditions } aggregates the values of the expression for every value of its iterators satisfying the conditions, as in sum{ facilities[i].cost | i in 1..size(facilities), facilities[i].flags[1] } or sum{ flow[i][j] * distance[location[i]][location[j]] | i in 1..n, j in 1..n }. size gives the length of any array, arrays of objects and arrays with several dimensions included, its undefined elements counted, whereas count gives the number of the defined values of an array of scalar values. Aggregators and membership skip undefined values, and a condition of an aggregation whose value is undefined is not satisfied. An undefined value read as a value outside an aggregation, or used as an index, makes the expression undefined, and an index outside the size of its dimension is an error.

Global attributes

Global attributes can be defined for a data store element as shown in the following example.

<bpmn2:dataStore id="DataStore_1">
<bpmn2:extensionElements>
<bpmnos:attributes>
<bpmnos:attribute id="Makespan" name="makespan := 0" type="decimal" objective="minimize" weight="1" />
</bpmnos:attributes>
</bpmn2:extensionElements>
</bpmn2:dataStore>

The objective value of a run is held by the system state and is not an attribute. It is the sum of the values of all weighted attributes multiplied by their weights: a global or data attribute contributes from its creation on and by every change of its value, and a status attribute contributes with its final value when its scope ends. Every change of the objective is announced by the objective notification.

Global attributes are visible to every process of a model, whether or not a process refers to the data store declaring them. They are data attributes held by the global state machine of a run, which holds the token of every process instance, and every scope inherits them as the first part of its data: the global attributes have the indices below the number of global attributes, the instance attribute every process declares first has that number as its index, and the further data attributes of a scope follow the data of its enclosing scopes. A write to a global attribute concerns every instance, a write to any other data attribute only the instance it belongs to.

Note
Modifying global attribute values may lead to race conditions.

Data attributes

Data attributes can be defined for a data object element as shown in the following example.

<bpmn2:extensionElements>
<bpmnos:attributes>
<bpmnos:attribute id="Instance" name="instance" type="string" />
</bpmnos:attributes>
</bpmn2:extensionElements>

Data attributes are similar to global attributes, however, they only exist within the scope cotaining the data object.

Note
Modifying data attribute values may lead to race conditions. However, when data attributes are only modified through activities within ad-hoc subprocesses with sequential ordering and the respective performer garantees sequential execution of all activties modifying a data attribute value, race conditions can be prevented.

Status attributes

Status attributes can be defined for a process element and an activity element as shown in the following example.

<bpmn2:extensionElements>
<bpmnos:status>
<bpmnos:attributes>
<bpmnos:attribute id="Timestamp" name="timestamp" type="decimal" />
</bpmnos:attributes>
</bpmnos:status>
</bpmn2:extensionElements>

Status attributes are attached to tokens moving through a process model. Their lifetime is restricted to the node that they are defined for and they are dynamically added and removed to the token status.

Restrictions

Restrictions allow to constrain the domain of attributes and to determine the sequence flows out of diverging gateways. Within a <bpmnos:restrictions> container any number of <bpmnos:restriction> elements can be provided to specify restrictions. For each restriction the following fields can be provided

  • id: a unique identifier,
  • scope: the scope indicating when the restriction has to be satisfied which must be one of entry, exit, full.
  • expression: an expression representing the requirements.

Node restrictions

Restrictions can be added to a process element and an activity element as shown in the following example.

<bpmn2:extensionElements>
<bpmnos:status>
<bpmnos:restrictions>
<bpmnos:restriction id="Restriction_3br81vk" expression="total_size &#60;= capacity" />
</bpmnos:restrictions>
</bpmnos:status>
</bpmn2:extensionElements>

A restriction of scope full of a process or subprocess also applies to every node within it, at the entry, completion and exit of that node, and is evaluated against the status and data of that node. An error or compensate event subprocess and a compensation activity do not inherit the restrictions of the scopes enclosing them, so that a violation within those scopes does not prevent its handling; the nodes within such an event subprocess inherit its own restrictions of scope full.

Gatekeeper restrictions

Gatekeeper restrictions can be added to a sequence flow element as shown in the following example.

<bpmn2:extensionElements>
<bpmnos:restrictions>
<bpmnos:restriction id="Restriction_222eo7i" expression="total_weight + weight &#62; capacity" />
</bpmnos:restriction>
</bpmnos:restrictions>
</bpmn2:extensionElements>

Conditions

The conditions of a conditional event, start, intermediate or boundary, are restrictions placed directly in its extension elements, as for a sequence flow; the event is triggered when all of them are satisfied, and a condition must not read the timestamp. Restrictions placed directly in the extension elements of any other node are refused, the restrictions of a node belonging to its status.

Operators

operators can be used to modify attribute values. Within an <bpmnos:operators> container any number of <bpmnos:operator> elements can be provided to specify operators. For each operator the following fields can be provided

  • id: a unique identifier,
  • expression: an expression assigning a value to an attribute.

Operators may be provided for tasks and events. A process, a subprocess and an event-subprocess have no operators, and a model declaring operators for one of them is refused; what is to happen when a scope starts is stated by the operators of its start event. The operators of a regular task and of a send task are applied when the task is performed, after its entry restrictions have been checked, those of a send task before its message is sent. The operators of a receive task and of a decision task are applied upon completion, after the message has been received or the choices have been made. The operators of a catch event, start events included, are applied when the event is triggered, after the message or signal it receives has been taken; those of an untyped start event, which awaits no trigger, when it is passed. The operators of a throw event, end events included, are applied before the event throws, so that a message or signal it throws carries the values they produce; those of an untyped end event, which throws nothing, when it is reached. The entry restrictions of a scope are checked after the operators of its start event have been applied, so that they constrain the status those operators produce. A scope is started as often as it is entered, so the operators of the start event of a looped or of a multi-instance subprocess are applied once per iteration and once per instance respectively.

Attention
Operators of an event must not modify the timestamp attribute, an event being instantaneous. The same holds for a send task, a receive task and a decision task, each of which completes upon an event of its own. Only a regular task may advance the timestamp, which is how its duration is modelled.

The following shows an example of an operator increasing an attribute value.

<bpmn2:extensionElements>
<bpmnos:status>
<bpmnos:operators>
<bpmnos:operator id="Operator_30a3lhs" expression="total_value += value" />
</bpmnos:operators>
</bpmnos:status>
</bpmn2:extensionElements>

The following shows an example using a lookup, an input that must be declared by a data store.

<bpmn2:extensionElements>
<bpmnos:status>
<bpmnos:operators>
<bpmnos:operator id="Operator_2ldkdhd" expresion="cost := cost(client,instance)" />
</bpmnos:operators>
</bpmnos:status>
</bpmn2:extensionElements>

Writing objects

An operator writes an object in one of three ways. An assignment to an element, location[i] := j, grid[i][j] += 1 or facilities[i].open := true, writes a value, and an assignment of an array or object to an element, grid[i] := [ 1, 2, 3 ] or facilities[i] := { cost := 5.0 }, writes its values into that element. An assignment to the whole object, facilities := [ ... ], replaces it. The value of an array or object assigned is a literal, an object attribute, route := tour, or a path to an array or object, route := facilities[2].stops; any other value, arithmetic in particular, is refused when the model is parsed. Finally, resize(path) := n gives the dimension the path addresses the length n, a non-negative integer: growing appends undefined elements, shrinking drops elements from the end, and the dimension of a field changes in every element of the enclosing array, so that all elements keep the same lengths.

An array or object assigned must have the value types and fields of the object it is assigned to; it is never converted from one value type to another, so that a decimal array is assigned [ 1.0, 2.0 ] rather than [ 1, 2 ]. Lengths change only as follows. An assignment, to the whole object or to an element, keeps the length of every fixed dimension, i.e. one fixed by the type or by a size declaration, a shorter value being padded with undefined values and a longer one being cut off if only undefined values are cut and an error otherwise, and gives every open dimension the length of the value. Within an element, an open dimension takes the length of the value in every element of the enclosing array, so that all elements keep the same lengths; a field the value omits has no elements in its open dimensions. An index beyond the current length is an error. Only resize changes a fixed length, which stays fixed.

Objects are shared until they are written: a token copied at a gateway, a candidate evaluated by a controller and a fork of a run hold the objects of the status and data they copy, and a write copies an object only if someone else holds it. Writing objects and changing their sizes should therefore be confined to what the run requires, and data that is only read belongs in global or data objects that no operator writes. At a converging gateway and at the completion of a multi-instance activity, the status objects of the tokens merge: every dimension takes the largest length the objects have, and each value is merged from the objects holding it as a status value is, values that agree being kept, an undefined value being no conflict, and a conflict making the value undefined. A data update names a written data object, not its elements.

Choices

Decision tasks are represented by task elements with an additional field bpmnos:type="Decision". For these decision tasks, choice on the value fo one or more attributes can be made. Within a <bpmnos:decisions> container any number of <bpmnos:decision> elements can be provided to define the respective attributes as shown in the following example.

<bpmn2:extensionElements>
<bpmnos:status>
<bpmnos:decisions>
<bpmnos:decision id="Decision_0udt1qg" condition="wait_type in [&#34;wait&#34;, &#34;break&#34;, &#34;rest&#34;]" />
</bpmnos:decisions>
</bpmnos:status>
</bpmn2:extensionElements>

Each condition constrains the values that may be chosen for the specified attribute.

Messages

Messages can be used to exchange information by delivering a content object from one process to another.

For message throw events and message catch events a <bpmnos:message> element must be provided with field name representing a name of the message and, if the message has content, field type stating the type of its content in the syntax of attribute types. The type is an object, { order: string, duration: decimal }, a scalar type being refused; a single value is sent as the field of an object. A message without content states no type. Every sender and receiver that may exchange a message states the same type, two types being the same if they have the same fields, in any order, of the same types, at every depth, and the same dimensions with the same sizes; a model in which they differ is refused. Message definitions may contain one or more parameters defining a message header, where the name field represents a name for the header entry and the value field states the value held under it. The value states the name of a declared attribute, in which case the entry holds the value of that attribute and is of the type the attribute is declared with, or a quoted string, in which case the entry holds that string. Nothing else may be stated, so that the type of every entry is known when the model is read. A parameter that states no value at all is permitted and means that the entry holds no value, which every value held under that name matches. By default, every header contains entries with names sender and recipient, which hold instance identifiers; the name of the message is no entry of the header, so that a parameter named name states an entry as any other parameter does. Messages can only be delivered to a recipient if the recipient specifies the same message name as the sender, the entry names of the headers are identical, the entries of the same name are of the same type wherever both sender and recipient state one, and all header values match, i.e. either have the same value or one of both is undefined.

The content of a message is one object of its type, the content object, which the operators of the throwing and the catching element refer to by the name of the message and which no other expression sees. The operators of a throwing element, a send task or a message throw event, write the content object, field by field, Request.order := instance, or as a whole, starting from an object of the type whose values are all undefined, in the sizes the instance data may declare at the throwing element; the object they leave is sent, a field no operator assigns being undefined. The operators of a catching element, a receive task or a message catch event, read the content object received, order := Request.order, and may not write it. A field holding an array or object is assigned to an attribute as a whole assignment is: the attribute keeps the lengths of its fixed dimensions, a shorter array being padded with undefined values and a longer one being an error, and takes the lengths of its open ones.

The following shows an example of an outgoing message definition for a send task sending a message with name Request to a recipient that must also have a parameter named machine having the value of the machine attribute. Its operators write the values of the instance and duration attributes into the content object.

<bpmn2:extensionElements>
<bpmnos:status>
<bpmnos:operators>
<bpmnos:operator id="Operator_Order" expression="Request.order := instance" />
<bpmnos:operator id="Operator_Duration" expression="Request.duration := duration" />
</bpmnos:operators>
</bpmnos:status>
<bpmnos:message name="Request" type="{ order: string, duration: decimal }">
<bpmnos:parameter name="machine" value="machine" />
</bpmnos:message>
</bpmn2:extensionElements>

The following shows an example of an incoming message definition for a message catch event receiving a message with name Request from a sender that must also have a parameter named machine having the value of the machine attribute. Its operators set the attributes order and duration to the fields of the content object.

<bpmn2:extensionElements>
<bpmnos:status>
<bpmnos:operators>
<bpmnos:operator id="Operator_Order" expression="order := Request.order" />
<bpmnos:operator id="Operator_Duration" expression="duration := Request.duration" />
</bpmnos:operators>
</bpmnos:status>
<bpmnos:message name="Request" type="{ order: string, duration: decimal }">
<bpmnos:parameter name="machine" value="machine" />
</bpmnos:message>
</bpmn2:extensionElements>

A message may also instantiate a process, which it does where the process has a message start event. Such a message names no recipient, the instance not existing before the message arrives, and is matched by its name alone. No element other than that start event may therefore catch a message of that name, and neither the start event nor any element throwing the message may state header parameters or a recipient. Several elements may throw it, each instantiating a process of its own, and a multi-instance send task instantiates one process per instance. A process cannot send itself a message, a message flow connecting two participants, so the message must be thrown outside the process it instantiates. The instance receives a generated identifier, and the operators of its start event read the content object of the message.

Signals

Signals can be used to broadcast a content object to whoever is listening for them.

For signal throw events and signal catch events a <bpmnos:signal> element must be provided with field name representing a name of the signal and, if the signal has content, field type stating the type of its content, an object as for a message; every thrower and catcher of a signal states the same type. The operators of the throwing element write the content object and those of each catching element read it, as for a message.

A signal has no header and no parameters, and this is what distinguishes it from a message. A message is delivered to one recipient, which is chosen among those a message flow and a matching header admit; a signal is broadcast to every element waiting for a signal of that name at the moment it is thrown, and to none if nothing is waiting, in which case it is simply lost. It states no sender and no recipient, so a model that wants the thrower known declares it as part of the content, as the following example does.

<bpmn2:extensionElements>
<bpmnos:status>
<bpmnos:operators>
<bpmnos:operator id="Operator_Origin" expression="Cancellation.origin := instance" />
<bpmnos:operator id="Operator_Reason" expression="Cancellation.reason := reason" />
</bpmnos:operators>
</bpmnos:status>
<bpmnos:signal name="Cancellation" type="{ origin: string, reason: string }" />
</bpmn2:extensionElements>

The content object is fixed when the signal is thrown, so that a recipient modifying a global attribute cannot change what another recipient receives. The sizes of its arrays may be declared in the instance data by the name of the signal, so that every signal of a name, also one raised by the environment, has the same layout. Each recipient writes the fields it needs to attributes of its own, which need not be named alike.

A signal may also instantiate a process, which it does where the process has a signal start event. Such a process is instantiated whenever a signal of that name is thrown, including by itself, the specification giving no ground to forbid a process instantiating itself where a signal rather than a message carries the trigger. An unguarded re-throw does not terminate.

Errors and escalations

Errors and escalations carry a content object from the element throwing them to the element catching them, as signals do.

An error end event, an error boundary event and an error start event may provide a <bpmnos:error> element, and an escalation throw event, an escalation boundary event and an escalation start event may provide a <bpmnos:escalation> element, each with field name representing the name of the error or escalation and, if it has content, field type stating the type of its content, an object as for a signal; every thrower and catcher of an error or escalation of a name states the same type. The operators of the throwing element write the content object and those of the catching element read it, as for a signal, the sizes of its arrays being declared in the instance data at the throwing element, as for a message.

An error or escalation is propagated from the element throwing it through the enclosing scopes until an element catches it, and its content is handed on with it; the status of the thrower is not handed on, so that the catching element and every scope the error or escalation passes keep their own status. An element stating a <bpmnos:error> or <bpmnos:escalation> element catches only an error or escalation of that name, whereas an element stating none catches every error or escalation, reading no content. An element throwing an error or escalation without stating its name throws one that only elements stating none catch, and so does the failure of a token violating a restriction, which is an error without a name. Where several elements could catch an error or escalation at the same scope, one stating its name takes precedence over one stating none.

<bpmn2:extensionElements>
<bpmnos:status>
<bpmnos:operators>
<bpmnos:operator id="Operator_Shortage" expression="Shortage.missing := demand - stock" />
</bpmnos:operators>
</bpmnos:status>
<bpmnos:error name="Shortage" type="{ missing: integer }" />
</bpmn2:extensionElements>

Timer

The trigger for a timer event can be specified by providing a parameter with name trigger and value being an expression as shown in the following example.

<bpmn2:extensionElements>
<bpmnos:timer>
<bpmnos:parameter name="trigger" value="timestamp + 5" />
</bpmnos:timer>
</bpmn2:extensionElements>

Inputs

Inputs provide data that is given once for a run and only read. They are declared by adding the following extension elements to a data store element.

<bpmn2:dataStore id="DataStore_2">
<bpmn2:extensionElements>
<bpmnos:inputs>
<bpmnos:input id="Input_1" name="costs" type="lookup" source="costs.csv" schema="From: string;To: string;Costs: decimal" />
<bpmnos:input id="Input_2" name="distance" type="matrix" source="distance.csv" schema="decimal[][]" />
<bpmnos:input id="Input_3" name="depots" type="object" source="depots.json" schema="{ x: decimal, name: string }[]" />
</bpmnos:inputs>
</bpmn2:extensionElements>
</bpmn2:dataStore>

The parameter name specifies the name by which expressions refer to the input, in every expression of a model, whether or not a process refers to the data store declaring it; the names of inputs and attributes must differ. The parameter type specifies the kind of input, lookup, matrix or object. The parameter source specifies the file name of the input, which is found in the working directory or in the folders given to the constructor of the model, or whose content is given to the constructor. The parameter schema specifies the type of the input.

A lookup is a CSV file with a header line, and becomes a function of its name, costs(client, server). Its schema states every column of the table with its type, name: type, separated by semicolons, in the syntax of attribute types; the names must agree with the header line of the file. The keys, all columns but the last, are scalar, whereas the result, the last column, may be an array or object, Destinations: string[]. Every cell is checked against the type of its column when the table is loaded: a string is quoted, a boolean, integer or decimal is a number or truth value, and an array or object is a literal whose value types and fields are those of the column and which fits its sizes. A lookup returning an array may only be the entire value of an assignment to an array, departures := departures(origin, destination) or the initial value of an object, and any other use is refused when the model is parsed.

A matrix is a CSV file without a header line, whose rows have equally many cells, and its schema is an array with two dimensions, decimal[][] or { x: decimal, y: decimal }[][], every cell holding a value or a literal of its base. An object is a JSON file, whose arrays are dimensions, whose objects are values with fields named by their keys, and whose numbers, truth values and strings are values of the types the schema states, null being undefined; the arrays at an open dimension have equal lengths. A matrix and an object are read and fitted to their schema when the model is loaded, a fixed dimension being padded with undefined values and a larger input being an error, and are read by their name in expressions as an object is, distance[i][j], sum(flow[i]) or depots[k].name. An input is never written: an assignment to it or to a part of it is refused when the model is parsed.

Data that is only read during a run, such as distances, flows or cost tables, belongs in inputs, which are held once and never copied, whereas global attributes and objects hold what changes during a run.

Loop parameters

For loop and multi-instance activities, additional parameters can be specified:

  • The cardinality parameter specifies the number of instances to be generated (only for multi-instance activities).
  • The index parameter specified the name of an attribute in which the index of the instance is stored (only for multi-instance activities).
  • The condition parameter specifies an attribute whos boolean value must be true in order to continue with another loop (only for loop activities).
  • The maximum parameter specifies the maximum number of loops that may be conducted (only for loop activities).
